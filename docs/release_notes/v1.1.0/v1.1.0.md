# KubeBlocks 1.1.0 (2026-06-30)

We are glad to announce the release of KubeBlocks 1.1.0.

KubeBlocks 1.1.0 focuses on safer instance-level change management, richer sharding operations, component-level network control, and stronger operational APIs for production database workloads.

## Highlights

### Dynamic InstanceSet Template Adoption

KubeBlocks now supports dynamically moving existing instances into named instance templates by ordinal.

This enables users to tune selected instances with different resources, service versions, component definitions, labels, annotations, scheduling policies, or volume claim templates while preserving instance identity and PVC semantics where possible.

### Sharding Enhancements

KubeBlocks enhances sharding support with:

* **Lifecycle Actions**: Addon authors can define hooks (`shardAdd`, `shardRemove`, `postProvision`, `preTerminate`) for sharding components
* **Shard-Specific Scale-In**: Operators can target an individual shard during scale-in via `spec.shardings[*].offline`
* **Heterogeneous Shards**: `spec.shardings[*].shardTemplates` allows individual shards to use different replicas, resources, versions, or component definitions

### Component Network Configuration

Cluster components can now declare network settings directly in `spec.componentSpecs[*].network`. Supported settings include:

- `hostNetwork`
- `hostPorts`
- `hostAliases`
- `dnsPolicy`
- `dnsConfig`

### Rollout API (Experimental)

KubeBlocks introduces the `Rollout` API (`apps.kubeblocks.io/v1alpha1`) for controlled instance rollout workflows. Rollout supports in-place updates, instance replacement, create/canary strategy, sharding rollout, and rich rollout status tracking.

> This feature is experimental in 1.1: the API is `v1alpha1` and may change in future releases, and some capabilities (such as `promotion.condition`) are not yet supported. It is not yet recommended for production use. Feedback is welcome.

### Operational Reliability Improvements

Role probe can now return an optional version together with the role name, so KubeBlocks can reject stale role reports based on the database engine's own role epoch instead of relying only on Kubernetes event time.

### API Additions, Deprecations, and Removals

#### New Alpha APIs (Experimental)

* `rollouts.apps.kubeblocks.io/v1alpha1`
  * New experimental `Rollout` API for cluster instance rollout workflows.

* `instances.workloads.kubeblocks.io/v1`
  * Experimental `Instance` API is used as the foundation for InstanceSet-managed instances.

#### Updated APIs

* `clusters.apps.kubeblocks.io/v1`
  * `spec.componentSpecs[*].network` supports component-level network configuration including `hostNetwork`, `hostPorts`, `hostAliases`, `dnsPolicy`, and `dnsConfig`.
  * `spec.componentSpecs[*].instances[*]` can carry dynamic instance template settings including `serviceVersion`, `compDef`, `replicas`, and `ordinals`.
  * `spec.componentSpecs[*].ordinals` supports explicit ordinal assignment for component instances.
  * `spec.shardings[*].shardTemplates` supports heterogeneous shards.
  * `spec.shardings[*].offline` supports scaling in a specified shard.
* `shardingdefinitions.apps.kubeblocks.io/v1`
  * `spec.lifecycleActions` supports sharding-level hooks, including `shardAdd` and `shardRemove`, in addition to `postProvision` and `preTerminate`.

#### Deprecations

No new deprecations in 1.1.

#### Removals

* **Preflight API removed** [#10108](https://github.com/apecloud/kubeblocks/pull/10108)
  * The preflight API (`troubleshoot.sh/v1beta2`: `Preflight`, `HostPreflight`) has been removed from the KubeBlocks repository, including its CRD definitions (`config/crd/preflight`), Go types (`externalapis/preflight/v1beta2`), and related RBAC roles.
  * These CRDs were not shipped in the KubeBlocks Helm chart; they were used by the legacy `kbcli` preflight checks. If you still rely on preflight checks, use the upstream [troubleshoot.sh](https://troubleshoot.sh) tooling directly.

No `*.kubeblocks.io` APIs or CRD versions are removed in 1.1.

## Upgrade Notice

Upgrading from KubeBlocks 1.0.x to 1.1.0 is supported.
Existing database cluster pods are not restarted or recreated automatically by the operator upgrade. New 1.1 capabilities are opt-in and require users to update Cluster specs, Rollout resources, or addon versions as needed.

## Breaking and Behavioral Changes

* **Default host port range changed**: The Helm value `hostPorts.include` default changed from `1025-65536` to `55000-59999` to avoid conflicts with node ephemeral ports. Existing host-port allocations are preserved (they are recorded in the host-port ConfigMap), but **new** allocations come from the new range. If your environment depends on the old range, set `hostPorts.include` explicitly when upgrading.

* **Default component ServiceAccount naming changed**: When `spec.componentSpecs[*].serviceAccountName` is not set, KubeBlocks now creates a default ServiceAccount named `kb-{clusterName}-{compName}` instead of `kb-{componentdefinition.name}`. Existing workloads are kept on the old ServiceAccount to avoid unintended pod restarts; the new ServiceAccount is used after the workload is restarted or recreated.
