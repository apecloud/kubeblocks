# KubeBlocks 1.1.0 (2026-05-29)

We are glad to announce the release of KubeBlocks 1.1.0.

KubeBlocks 1.1.0 focuses on multi-cluster database management through the experimental Instance API, controlled rollout workflows for cluster instances, component-level network configuration, dynamic InstanceSet template adoption, and sharding enhancements, bringing finer-grained control and broader topologies to production environments.

## Highlights

### Dynamic InstanceSet Template Adoption

Supports dynamically assigning existing pods to named instance templates by ordinal. This lets users tune selected instances (resources, versions, component definitions) while preserving pod identity and PVC data.

### Sharding Enhancements

Sharding support now includes lifecycle actions, shard-specific scale-in, and heterogeneous shard templates:

* **Lifecycle Actions**: Addon authors can define hooks (`shardAdd`, `shardRemove`, `postProvision`, `preTerminate`) for sharding components
* **Shard-Specific Scale-In**: Operators can target an individual shard during scale-in via `spec.shardings[*].offline`
* **Heterogeneous Shards**: `spec.shardings[*].shardTemplates` allows individual shards to use different replicas, resources, versions, or component definitions

### Component Network Configuration

Adds component-level network configuration through `spec.componentSpecs[*].network`, including host networking, explicit host port mappings, pod host aliases, DNS policy, and DNS config.

### Multi-Cluster Support (Experimental)

Introduces multi-cluster database management built on the new `Instance` API. A single KubeBlocks control plane can manage database instances distributed across multiple Kubernetes data clusters, with placement controlled by annotations and Helm-level context configuration.

> This feature is experimental in 1.1: it is disabled by default, the APIs may change in future releases, and it is not yet recommended for production use. Feedback is welcome.

### Rollout API (Experimental)

This release adds the `Rollout` API (`apps.kubeblocks.io/v1alpha1`) and controller for cluster instance rollout workflows. Rollout supports in-place updates, instance replacement, create/canary strategy, sharding rollout, and rich rollout status tracking.

> This feature is experimental in 1.1: the API is `v1alpha1` and may change in future releases, and some capabilities (such as `promotion.condition`) are not yet supported. It is not yet recommended for production use. Feedback is welcome.

### KubeBlocks Addon Highlights

* **MySQL Enhancements**: Adds mydumper backup, audit log, shell-triggered reconfigure, and new version support
* **Redis TLS & Redis 8**: Adds TLS encryption, Redis 8 support, redis-exporter metrics, and retry-safe shard lifecycle actions
* **PostgreSQL Refactor**: Refactors the PostgreSQL addon with PostgreSQL 18 support and pg_dump/pg_dumpall backup

### API Additions, Deprecations, and Removals

#### New Alpha APIs (Experimental)

* `rollouts.apps.kubeblocks.io/v1alpha1`
  * New experimental `Rollout` API for cluster instance rollout workflows.

* `instances.workloads.kubeblocks.io/v1`
  * Experimental `Instance` API is used as the foundation for InstanceSet-managed instances and multi-cluster placement.

#### Updated APIs

* `clusters.apps.kubeblocks.io/v1`
  * `spec.componentSpecs[*].network` supports component-level network configuration including `hostNetwork`, `hostPorts`, `hostAliases`, `dnsPolicy`, and `dnsConfig`.
  * `spec.componentSpecs[*].instances[*]` can carry dynamic instance template settings including `serviceVersion`, `compDef`, `replicas`, and `ordinals`.
  * `spec.componentSpecs[*].ordinals` supports explicit ordinal assignment for component instances.
  * `spec.shardings[*].shardTemplates` supports heterogeneous shards.
  * `spec.shardings[*].offline` supports scaling in a specified shard.
* `shardingdefinitions.apps.kubeblocks.io/v1`
  * `spec.lifecycleActions` supports sharding-level hooks, including `shardAdd` and `shardRemove`, in addition to `postProvision` and `preTerminate`.

#### Deprecations

No new deprecations in 1.1.

#### Removals

* **External preflight API removed** [#10108](https://github.com/apecloud/kubeblocks/pull/10108)
  * The vendored external preflight API (`troubleshoot.sh/v1beta2`: `Preflight`, `HostPreflight`) has been removed from the KubeBlocks repository, including its CRD definitions (`config/crd/preflight`), Go types (`externalapis/preflight/v1beta2`), and related RBAC roles.
  * These CRDs were not shipped in the KubeBlocks Helm chart; they were used by the legacy `kbcli` preflight checks. If you still rely on preflight checks, use the upstream [troubleshoot.sh](https://troubleshoot.sh) tooling directly.

No `*.kubeblocks.io` APIs or CRD versions are removed in 1.1.


#### Configuration and Annotation Additions

* Helm values add `multiCluster.kubeConfig`, `multiCluster.contexts`, `multiCluster.contextsDisabled`, and `multiCluster.mountPath` for multi-cluster controller configuration.
* Multi-cluster placement annotations include:
  * `apps.kubeblocks.io/multi-cluster-placement`
  * `apps.kubeblocks.io/multi-cluster-service-placement`
  * `apps.kubeblocks.io/multi-cluster-object-provision-policy`

## Upgrade Notice

Upgrading from 1.0.x to 1.1.0 is supported. Upgrading the operator does not restart or recreate the pods of existing database clusters; existing clusters keep working without manifest changes, and all 1.1 features are opt-in.

:::note
Helm does not upgrade CRDs. You must update the CRDs manually before upgrading the chart.
:::

### Upgrade Steps

1. Install or update CRDs before upgrading the chart. Snapshot CRDs must exist before KubeBlocks is installed. For KubeBlocks CRDs, create CRDs that do not exist yet, then replace existing CRDs with the 1.1.0 release asset:

```bash
kubectl get crd volumesnapshots.snapshot.storage.k8s.io || kubectl create -f deploy/helm/crds/snapshot/
kubectl get crd rollouts.apps.kubeblocks.io || kubectl create -f deploy/helm/crds/apps.kubeblocks.io_rollouts.yaml
kubectl get crd instances.workloads.kubeblocks.io || kubectl create -f deploy/helm/crds/workloads.kubeblocks.io_instances.yaml
kubectl replace -f https://github.com/apecloud/kubeblocks/releases/download/v1.1.0/kubeblocks_crds.yaml
```

2. Upgrade the Helm release:

```bash
helm repo update
helm -n kb-system upgrade kubeblocks kubeblocks/kubeblocks --version 1.1.0 --skip-crds
```

3. Verify the upgrade:

```bash
kubectl -n kb-system get pods
kubectl get crd rollouts.apps.kubeblocks.io instances.workloads.kubeblocks.io
kubectl get clusters -A   # existing clusters must stay Running
```

### Breaking and Behavioral Changes

* **Default host port range changed**: The Helm value `hostPorts.include` default changed from `1025-65536` to `55000-59999` to avoid conflicts with node ephemeral ports. Existing host-port allocations are preserved (they are recorded in the host-port ConfigMap), but **new** allocations come from the new range. If your environment depends on the old range, set `hostPorts.include` explicitly when upgrading.
* **Removed Helm value**: `enabledAlphaFeatureGates.recoverVolumeExpansionFailure` has been removed. Remove it from your values files; enable the corresponding Kubernetes feature gate on the cluster directly if needed.
* **New Helm values for default container resources**: `clusterDefaultResources` (init/sidecar containers of managed workloads), `dataProtection.zeroResourceForUnset`, `operations.zeroResourceForUnset`, and `addonController.jobResources`. Defaults preserve the 1.0 behavior; review them if your namespaces enforce `LimitRange` policies.
