# KubeBlocks 1.1.0 (2026-05-29)

We are glad to announce KubeBlocks 1.1.0.

KubeBlocks 1.1.0 focuses on multi-cluster management through the experimental Instance API, cluster instance rollout workflows, component-level network configuration, dynamic InstanceSet template adoption, sharding enhancements, and volume sharing among instances.

## Highlights

### Multi-Cluster Support Through the Instance API

KubeBlocks 1.1.0 uses the experimental `Instance` API as the foundation for multi-cluster database management. A single KubeBlocks control plane can manage database instances distributed across multiple Kubernetes data clusters.

### Rollout for Cluster Instances

This release adds the experimental `Rollout` API and controller for cluster instance rollout workflows. Rollout supports cluster instance replacement, create strategy, sharding rollout, canary-style updates, and richer rollout status tracking.

### ComponentNetwork API

KubeBlocks 1.1.0 adds component-level network configuration through `spec.componentSpecs[*].network`, including host networking, explicit host port mappings, pod host aliases, DNS policy, and DNS config.

### Dynamic InstanceSet Template Adoption

KubeBlocks 1.1.0 supports dynamically assigning existing pods to named instance templates by ordinal. This lets users tune selected instances while preserving pod identity and PVC data.

### Sharding Enhancements

Sharding support now includes lifecycle actions, shard-specific scale-in, and heterogeneous shard templates. Addon authors can define lifecycle hooks (`shardAdd`, `shardRemove`, `postProvision`, `preTerminate`) for sharding components; operators can target an individual shard during scale-in via `spec.shardings[*].offline` instead of changing the whole sharding topology at once; and `spec.shardings[*].shardTemplates` allows individual shards to use different replicas, resources, versions, or component definitions.

### Volume Sharing Among Instances

KubeBlocks 1.1.0 allows different instances to share an existing PersistentVolumeClaim. The PVC template in the Cluster and Component APIs adds `persistentVolumeClaimName`, so multiple instances can mount the same volume (for example, a shared `ReadWriteMany` volume) instead of always provisioning per-instance PVCs.

## API Changes

### New APIs

* `rollouts.apps.kubeblocks.io/v1alpha1`
  * New experimental `Rollout` API for cluster instance rollout workflows.
  * Key spec fields: `spec.clusterName`, `spec.components`, `spec.shardings`.
  * Component rollout fields include `serviceVersion`, `compDef`, `strategy`, `replicas`, and `instanceMeta`.
  * Sharding rollout fields include `shardingDef`, `serviceVersion`, `compDef`, `strategy`, `replicas`, and `instanceMeta`.
  * Strategy fields include `strategy.inplace`, `strategy.replace`, and `strategy.create`; create strategy supports canary and promotion settings.
  * Status fields include `status.state`, `status.conditions`, `status.components`, and `status.shardings`.

* `instances.workloads.kubeblocks.io/v1`
  * Experimental `Instance` API is used as the foundation for InstanceSet-managed instances and multi-cluster placement.
  * Key spec fields include `spec.template`, `spec.selector`, `spec.volumeClaimTemplates`, `spec.instanceSetName`, `spec.instanceTemplateName`, update policies, roles, lifecycle actions, configs, assistant objects, and `spec.scaledDown`.
  * Status fields include readiness/availability, role, revision, config status, and volume expansion state.

* `parameterviews.parameters.kubeblocks.io/v1alpha1`
  * New `ParameterView` API in the parameters group.

### Updated APIs

* `clusters.apps.kubeblocks.io/v1`
  * Adds component-level network configuration at `spec.componentSpecs[*].network`.
  * `network` supports `hostNetwork`, `hostPorts`, `hostAliases`, `dnsPolicy`, and `dnsConfig`.
  * `spec.componentSpecs[*].instances[*]` can carry dynamic instance template settings including `serviceVersion`, `compDef`, `replicas`, and `ordinals`.
  * `spec.componentSpecs[*].ordinals` supports explicit ordinal assignment for component instances.
  * `spec.componentSpecs[*].volumeClaimTemplates[*].persistentVolumeClaimName` supports referencing an existing PVC so multiple instances can share a volume.
  * `spec.shardings[*].shardTemplates` supports heterogeneous shards with per-template `shards`, `shardIDs`, `serviceVersion`, `compDef`, `replicas`, `resources`, `volumeClaimTemplates`, and scheduling policy.
  * `spec.shardings[*].offline` supports scaling in a specified shard.
  * `status.shardings` reports per-sharding phase and lifecycle action status (`postProvision`, `preTerminate`).

* `instancesets.workloads.kubeblocks.io/v1`
  * `spec.instances[*]` supports named instance templates with `replicas` and `ordinals`.
  * `spec.flatInstanceOrdinal` controls whether pod naming uses a flattened ordinal scheme across instance templates.
  * `status.templatesStatus` reports per-template replica status.
  * `status.assignedOrdinals` records ordinal assignment for templates.

* `shardingdefinitions.apps.kubeblocks.io/v1`
  * `spec.lifecycleActions` supports sharding-level hooks.
  * New sharding lifecycle hooks include `shardAdd` and `shardRemove`, in addition to `postProvision` and `preTerminate`.
  * `ShardingAction.targetShardSelector` supports targeting `Any` or `All` shards.

* `componentdefinitions.apps.kubeblocks.io/v1`
  * `spec.disableDefaultHeadlessService` disables creation of the default headless service.
  * File templates support declared `variables` (`FileTemplateVariable`) with name, description, and default value.

### Deprecated APIs

No new deprecations in 1.1. The legacy `apps.kubeblocks.io/v1alpha1` resources (`Cluster`, `ClusterDefinition`, `Component`, `ComponentDefinition`, `ComponentVersion`, `ServiceDescriptor`) remain deprecated since 1.0 in favor of `apps.kubeblocks.io/v1`; they are still served for backward compatibility, and `v1` remains the storage version. Migrate remaining v1alpha1 manifests to `v1` before the v1alpha1 versions are removed in a future release.

### Removed APIs

No APIs or CRD versions are removed in 1.1.

### Configuration and Annotation Additions

* Helm values add `multiCluster.kubeConfig`, `multiCluster.contexts`, `multiCluster.contextsDisabled`, and `multiCluster.mountPath` for multi-cluster controller configuration.
* Multi-cluster placement annotations include:
  * `apps.kubeblocks.io/multi-cluster-placement`
  * `apps.kubeblocks.io/multi-cluster-service-placement`
  * `apps.kubeblocks.io/multi-cluster-object-provision-policy`

## Upgrading from 1.0.x to 1.1

Helm does not upgrade CRDs, so the CRDs must be updated manually before upgrading the chart.

1. Update CRDs (this also installs the new `Rollout`, `Instance`, and `ParameterView` CRDs):

```bash
kubectl replace -f https://github.com/apecloud/kubeblocks/releases/download/v1.1.0/kubeblocks_crds.yaml
```

2. Upgrade the Helm release:

```bash
helm repo update
helm -n kb-system upgrade kubeblocks kubeblocks/kubeblocks --version 1.1.0
```

3. Verify the upgrade:

```bash
kubectl -n kb-system get pods
kubectl get crd rollouts.apps.kubeblocks.io instances.workloads.kubeblocks.io
kubectl get clusters -A   # existing clusters must stay Running
```

Upgrading the operator must not restart or recreate the pods of existing database clusters. Existing clusters keep working without manifest changes; all 1.1 features are opt-in.

### Breaking and Behavioral Changes

* **Default host port range changed.** The Helm value `hostPorts.include` default changed from `1025-65536` to `55000-59999` to avoid conflicts with node ephemeral ports. Existing host-port allocations are preserved (they are recorded in the host-port ConfigMap), but **new** allocations come from the new range. If your environment depends on the old range, set `hostPorts.include` explicitly when upgrading.
* **Removed Helm value:** `enabledAlphaFeatureGates.recoverVolumeExpansionFailure` has been removed. Remove it from your values files; enable the corresponding Kubernetes feature gate on the cluster directly if needed.
* **New Helm values for default container resources:** `clusterDefaultResources` (init/sidecar containers of managed workloads), `dataProtection.zeroResourceForUnset`, `operations.zeroResourceForUnset`, and `addonController.jobResources`. Defaults preserve the 1.0 behavior; review them if your namespaces enforce `LimitRange` policies.

See [API Changes](#api-changes) for the full list of new, updated, deprecated, and removed APIs.

### Other Upgrade Notes

* Review manifests that use multi-cluster placement annotations, rollout, `spec.componentSpecs[*].network`, dynamic instance templates, or sharding lifecycle hooks before upgrading production clusters.
* Multi-cluster support requires new Helm values (`multiCluster.kubeConfig`, `multiCluster.contexts`); it is disabled by default.
* Verify the active Kubernetes context before running cluster-level upgrade, install, or e2e commands.
